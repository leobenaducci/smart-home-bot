# home-search

SearXNG and Vane — the house's own metasearch, and an answering engine that
reads the pages for you. They are what the assistant's `searxng` and `vane`
skills talk to.

```
assistant  --HTTP-->  searxng :21032
           --HTTP-->  vane    :21033  --> searxng, over the compose network
                                     --> the same Ollama the assistants use
```

**Off by default.** It is two more images on a stack that already builds
twelve services, and the assistant works without it — `web_search` falls back
to its own provider. Turn it on in `config/home-stack.yml`:

```yaml
services:
  home-search:
    enabled: true
```

Turning it on does two things beyond starting the containers, both handled by
the deploy: the `searxng` and `vane` skills come off the assistants'
`disabledSkills`, and `web_search` is pointed at the house instance. Turning it
off puts them back. That switch is the point — see *Why the skills are
disabled, not just unconfigured* below.

| | |
|---|---|
| Role | `compute`. Nothing here needs to be near the assistants; they reach it over HTTP, so the only coupling is an address. On the default single-box install every role is `127.0.0.1`. |
| Config | `{paths.config}/home-search/searxng/settings.yml`, seeded once from `settings.example.yml` and **state** afterwards. |
| Secret | `SEARXNG_SECRET_KEY`, generated by `./home-stack install --generate-secrets`. |
| Model | Vane uses the same Ollama the assistants do, from `derived.ollama_url`. |
| What the skills read | `SEARXNG_BASE_URL` and `VANE_BASE_URL`, exported into the assistants by the deployer. These are the names to check when a skill says "did not answer". |

## Before the first deploy

Vane needs **two** models on the Ollama host, not one — a chat model and an
embedding model. With either missing, every `/api/search` answers 400 while the
container looks perfectly healthy:

```bash
ollama pull llama3.1
ollama pull nomic-embed-text
```

`test/check.py` asks for both and names the one that is missing, so this is a
failed deploy rather than a puzzle later.

## The two settings that decide whether it works

Both live in `settings.yml`, both are checked by `validate-settings.py` before
anything is replaced, and both fail the deploy rather than producing an
instance that looks healthy and refuses every call.

- **`search.formats` must include `json`.** It is not in SearXNG's default
  list, and without it `/search?format=json` answers 403 with an HTML body —
  which reads as "the instance is broken" rather than "it is not serving JSON".
  That endpoint is the whole contract the `searxng` skill is built on.
- **`server.limiter` must be explicitly `false`.** The limiter answers 429 to
  anything whose User-Agent looks like a script, which is exactly what the
  assistant is. *Absent* counts as wrong: not because the image's default is on
  — it ships `false` — but because this is the setting that decides whether the
  instance answers the assistant at all, and inheriting it from an upstream
  nobody here controls is how it changes without anybody noticing.

## Things that were learned the hard way

**The config is seeded once, then it is yours.** `settings.example.yml` is
copied to `{paths.config}/home-search/searxng/settings.yml` on the first deploy
and never again. Editing the example after that changes nothing on a machine
that has already deployed; edit the deployed file, or delete it and re-deploy.
The secret is substituted in only while the file still carries the image's
`ultrasecretkey` placeholder, so rotating `SEARXNG_SECRET_KEY` does *not*
rotate a running instance's — change it in the deployed file.

**`FORCE_OWNERSHIP=false`, or the deploy works exactly once.** The image runs
as root and its entrypoint chowns the config path to its own uid on first boot.
The next deploy then cannot write the settings file it exists to install: EPERM,
and a red deploy whose whole job was replacing that file. The directory belongs
to the deploy, and a container that seizes it is the bug — SearXNG only warns
about the ownership and needs nothing more.

**A `results` key is not a result.** An instance with no outbound DNS, or whose
upstreams are refusing a new IP, answers 200 with an empty array. A check that
asserted the key went green while every assistant call afterwards got "nothing
came back" — which the skill's own troubleshooting reads as an instance
problem. `test/check.py` requires an actual result and prints
`unresponsive_engines` when there is none.

**Vane reads `OLLAMA_BASE_URL`, whatever its README says.** Its README says
`OLLAMA_HOST`, and so does Ollama itself, so it is the obvious guess and it is
wrong. With the wrong name Vane boots with only its built-in Transformers
provider — embeddings and no chat model — and every `/api/search` 400s behind a
healthy container. `GET /api/providers` is the authority, which is why the
check reads it.

## Why the skills are disabled, not just unconfigured

With the service off, `searxng` and `vane` go on the assistants'
`disabledSkills` rather than being left to fail at call time. An unavailable
skill is not inert: `build_skills_summary` lists skills without filtering on
whether their environment is met, so its name and full description still enter
every prompt, marked unavailable — which invites the agent to try it,
apologise, and spend a family turn. Blanking the base URL does not help either: the compose
files supply it with a `:-` default, and that form substitutes for an empty
value as well as an unset one.

## Ports

`21032`, inside the stack's own 21000-21499 band, rather than SearXNG's own
`8080` — the number most likely to already mean something else on a machine you
also run a stack on. Only the host side moves; the container still listens on
8080, and `SEARXNG_PORT` is deliberately not passed into it, because the image's
entrypoint reads that name to choose its *internal* bind port. If it moves again, `services.home-search.port` moves
with it: the assistants are given the address from there, and a skill pointed at
the wrong port fails as "SearXNG did not answer".
